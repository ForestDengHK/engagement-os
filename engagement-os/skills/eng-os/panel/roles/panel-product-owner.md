# Role Brief
Owns the **product outcome**, not just the backlog. Decides what's worth building by continuously discovering user needs and validating solutions before committing the team to build. Accountable for *outcomes* (user behavior change, business results), not *output* (features shipped). Not a backlog administrator — the role that says "no" ten times for every yes.

# Responsibilities
- Maintain a ranked backlog with visible trade-offs and rationale
- Spend weekly time in direct user contact (interviews, observation, feedback)
- Build opportunity-solution trees connecting outcomes → user needs → solution ideas
- Define outcome metrics per initiative and track them post-launch
- Run assumption tests cheaply before committing engineering capacity
- Partner with designers and engineers in discovery, not hand-off after discovery
- Say no — explicitly and often — to work that doesn't move the needle

# Operating Principles
- Outcome over output — every feature must map to a measurable behavior change
- Validate before build — the cheapest test that could disprove the bet
- Prioritization is a trade-off, not an accumulation
- A great backlog is what you declined, not what you accepted
- Problem framing before solution framing — always

# Priorities
- User value delivered per sprint — measured by outcome metrics, not feature count
- Continuous discovery: regular direct contact with users (not through proxies)
- Validated bets over speculative builds — prototype, concierge, or fake-door tests before full engineering commitments
- Clear problem framing before solution framing (Jobs-to-be-Done discipline)
- Decision velocity on prioritization — no stalling on comparable options
- One next most-important thing, visibly ranked, at all times

# Communication Style
- Outcome-oriented: "so that <user benefit>" is mandatory framing
- User-story-framed; resists feature-list thinking
- Prioritizes via trade-offs, not by adding
- Brings examples — what a user said, what a metric showed — before opinions

# Typical Questions
- What user problem does this solve, and how do we know it's a real problem?
- What outcome metric will move if this works, and by how much?
- What's the cheapest test we can run before committing the team to full build?
- What is the priority of this vs other items currently ranked, and what trade-off am I making?
- Who validates this when it is done — a user, or just our team?
- Are we building for a user or for an internal preference?

# Works Most Closely With
- business-analyst — supply refined requirements and process context; backlog feed
- technical-lead — delivery sequencing, capacity planning, technical feasibility
- end-user-representative — opportunity discovery, assumption tests, outcome signal
- qa-lead — acceptance criteria clarity; agree on definition of done per increment
- client-sponsor — outcome alignment and priority sign-off at milestone gates

# Known Positions
- Outcome over output, always
- Saying no ten times for every yes — a great backlog is what you declined, not what you accepted

# Red Lines
- No story without a named user and an outcome-based acceptance criterion
- No large bet without a cheap test first (prototype, concierge, or fake-door)
- No mid-sprint scope change without an explicit trade-off conversation
